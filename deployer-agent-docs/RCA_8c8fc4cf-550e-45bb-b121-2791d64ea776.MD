# RCA — Admin PNG upload fails (`POST /api/admin/images/upload`)

**App:** wear-interactive (wearthehope.com) · frontend_type=cloudflare · tier_0 · active run `8c8fc4cf-550e-45bb-b121-2791d64ea776`
**Reported symptom:** Admin > Products PNG upload fails with a generic "something went wrong" toast.

## Answer to the specific questions
- **Max request body size enforced by production ingress:** the in-pod nginx sets `client_max_body_size 100M` (platform default nginx.conf, no override in GCS). So a 413 at the ingress only happens above ~100 MB — **not** the limiter for product photos.
- **Backend-enforced cap:** `/api/admin/images/upload` reads the whole body then rejects anything over **15 MB** → `HTTPException(413, 'File too large — 15 MB max')` (`backend/server.py` ~line 3927).
- **Pillow / "Could not process image":** `_process_image` is wrapped in `try/except` → any Pillow error returns `400 'Could not process image: {e}'` (~line 3931). DecompressionBombError only fires above ~179M pixels (2× `MAX_IMAGE_PIXELS` 89,478,485) — reproduced in sandbox: a 12000×12000 (144M px) image only warns and still opens; a >~13400×13400 PNG would raise and produce the 400.
- **S3 errors:** `_try_upload_to_s3` (`asyncio.to_thread`) catches all exceptions, logs `S3 upload failed … — falling back to GridFS`, and returns None → upload still succeeds via GridFS. **S3 is not a failure path.** No S3 warning observed in logs.
- **Recent upload requests in logs:** none for `/api/admin/images/upload` or `-from-url` in the last 24h (max window), despite admin being active (`POST /api/admin/products/reorder 200`). Consistent with the request being cut off before the uvicorn access log is written (see below), or no retry inside the window.

## Root cause(s) — in order of likelihood

### 1. Event-loop blocking during image processing → pod killed mid-upload (primary infra/code interaction)
`admin_upload_image_file` calls `_process_image(raw)` **directly and synchronously** inside the `async def` handler (`backend/server.py` ~3931). `_process_image` does `Image.open → convert → thumbnail(LANCZOS) → save(WEBP, method=6)` — all CPU-bound and blocking. Note the S3 upload in the same file DOES use `asyncio.to_thread`, but the image processing does NOT. With `uvicorn … --workers 1` this blocks the single event loop for the whole encode.

nginx `/health` is configured with `proxy_read_timeout 1s` and maps any 5xx/timeout from the backend to a 503. While the loop is blocked, the k8s probes hit that 503.

**Evidence — `get_pod_events` (run 8c8fc4cf):**
- `Liveness probe failed: HTTP probe failed with statuscode: 503` (×8)
- `Readiness probe failed: … 503` (×8), `Startup probe failed: … 503`
- `Killing … Stopping container` — pods `…-fhm8s` and `…-2f8fb` killed after the 503s.

When the serving pod is killed mid-request the client connection drops → the frontend shows the generic error toast, and no clean backend access-log line for the upload is written (matches the empty log search).

**Sandbox reproduction of the CPU cost (eph pod, Pillow 13.0.0):** flat-color PNGs encoded in 0.3–1.35s on the sandbox's generous CPU. Real photographic PNGs with LANCZOS downscale + WebP `method=6` are far heavier, and tier_0 caps CPU at **250m** (≈¼ core, well under the sandbox), so the same encode easily exceeds the 1s `/health` read timeout and stalls the lone worker.

### 2. 15 MB backend cap → 413 for large PNGs (very common, independent of #1)
Uncompressed / high-megapixel product PNGs routinely exceed 15 MB, so `/api/admin/images/upload` returns `413 'File too large — 15 MB max'`. nginx already permits 100 MB, so this cap is purely the app's own choice. Also note `raw = await file.read()` loads the entire body into memory *before* the size check.

### 3. Frontend swallows the real error (compounding)
The admin UI surfaces a generic "something went wrong" toast instead of the backend's specific 413/400 detail, so the admin cannot tell which case they hit. This hides #1/#2 and makes triage harder.

### 4. DecompressionBombError (edge case)
Only for PNGs above ~179M pixels → `400 'Could not process image: … decompression bomb …'`. Unlikely for normal product photos but possible for extreme-resolution source files.

## Secondary observation (not the upload bug, but a reliability risk)
The deployment is flapping between 1 and 2 replicas (`ScalingReplicaSet … 1→2 / 2→1`, count 42 over 2 days); the second replica repeatedly fails its **startup** probe with 503 and is killed, leaving a single healthy replica (`…-9qzzv`, 0 restarts). This likely shares the slow-boot / 1s health-probe-timeout sensitivity at tier_0 and should be investigated separately.

## Suggested fixes
- **Code (E1):** Offload CPU-bound image work off the event loop — wrap `_process_image` in `await asyncio.to_thread(_process_image, raw)` in BOTH `admin_upload_image_file` and `_store_image_from_url` (mirror the existing S3 `asyncio.to_thread` pattern). Consider lowering WebP `method` (6→4) to cut encode time. This stops uploads from tripping the 1s liveness probe.
- **Code (E1):** Raise/align the 15 MB cap (nginx allows 100 MB) or at minimum stream-check size; and surface the backend error detail (413/400 message) in the admin toast instead of a generic "something went wrong."
- **User (Resources tier):** tier_0 is CPU 250m / mem 512Mi. If image processing stays on-box, the 250m CPU cap is a real constraint for WebP encoding; raising the tier gives headroom (do this alongside the code fix, not instead of it).
- **User (verify):** Confirm the pixel dimensions / file size of the PNG(s) that fail, so we can distinguish the 15 MB-413 case from the event-loop-stall case.
